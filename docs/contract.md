# Internal integration contract

Node 24+ ESM, built-in node:sqlite, Express. HTTP serves `dist` SPA and JSON. API JSON errors `{error:{code,message}}`. Default binding 127.0.0.1:8787. Persistent data ignored `data/`. No real wallet/private credentials seeded. Demo mode explicitly flagged server-side, cannot settle live orders. Cookie authentication and server-side tenant authorization.

Frontend endpoint contract: merchant data endpoints require a merchant session. Authentication entry points, `/api/auth/me` and `/api/registry` are public; production demo mode further restricts account creation and live access. Public checkout endpoints use scoped checkout tokens.
- GET /api/auth/me -> `{user:null|{id,email,name}, mode:'demo'|'live'}`.
- POST /api/auth/register `{email,password,name}`; POST /api/auth/login `{email,password}`; POST /api/auth/logout; POST /api/auth/demo creates/logs into isolated demo merchant for local preview.
- GET /api/dashboard -> `{stats:{total_volume,paid_orders,pending_orders,success_rate},chart:[{date,amount}],recent_orders:[],chains:[],mode}`.
- GET /api/projects -> `{projects:[{id,name,description,webhook_url,created_at}]}`; POST /api/projects `{name,description,webhook_url?}`; PATCH /api/projects/:id.
- GET /api/orders?status=&q=&project_id= -> `{orders:[],total}`; POST /api/orders `{project_id,fiat_amount,fiat_currency,chain?,token_id?,merchant_order_id?,product_id?}` -> order; POST /api/orders/:id/cancel; POST /api/orders/:id/simulate `{confirmations?:integer}` ONLY isolated demo.
- order fields: `order_id,project_id,project_name,merchant_order_id,fiat_amount,fiat_currency,status,chain,token_id,pay_address,payable_amount,received_amount,payment_tolerance,created_at,expires_at,confirmations,required_confirmations,tx_hash,checkout_url,checkout_token,delivery?`. `received_amount` is the linked transfer's actual amount or null. `payment_tolerance` is null unless the server can prove a permitted stablecoin fingerprint waiver; then it contains `{enabled:true,kind:'fingerprint_only',minimum_amount,maximum_amount,maximum_shortfall,requires_unique_order:true}` with exact decimal strings. Do not infer a tolerance or actual receipt from the requested amount.
- GET /api/addresses -> `{addresses:[]}`; POST /api/addresses `{project_id,chain,address,label?,token_ids?}`; PATCH /api/addresses/:id `{enabled:boolean}`.
- GET /api/keys -> `{keys:[{id,key_id,key_prefix,project_id,name,created_at,revoked}]}`; POST /api/keys `{project_id,name}` -> `{key_id,secret,key_prefix}` (show once); DELETE /api/keys/:id.
- GET /api/webhooks -> `{deliveries:[],endpoints:[]}`; POST /api/webhooks `{project_id,url}` -> `{id,secret}`; POST /api/webhooks/:id/retry; POST /api/webhooks/test `{project_id}`.
- GET /api/transactions -> `{transactions:[]}` including unmatched; POST /api/transactions/:id/claim `{order_id}` requires approved project ownership, confirmed valid funds and the order's amount/time/network constraints. With the opt-in fingerprint waiver, the actual amount must still cover the verified base including merchant fees. Ambiguous automatic matches remain unassigned with `reason:'ambiguous_amount'` until explicitly reviewed; claim records `paid_source:'manual'`.
- GET /api/products -> `{products:[{id,project_id,name,price,currency,stock}]}`; POST /api/products `{project_id,name,price,currency}`; POST /api/products/:id/inventory `{items:string[]}`. Delivery visible only after paid, atomic one-use item allocation.
- GET /api/settings -> `{name,email,mode}`; PATCH /api/settings `{name}`.
- GET /api/registry public -> `{chains:[{id,name,family,confirmations,tokens:[{id,symbol,decimals}],configured:boolean}],currencies:[]}`.
- GET /checkout/:token/state JSON, GET /checkout/:token/methods JSON, POST /checkout/:token/select `{chain,token_id}`. SPA page /checkout/:token. State strictly public cropped data; include `mode,product_name,delivery` for demo store checkout, no metadata or credentials. Frontend polls at >=5 sec.

UI routes: /, /pricing, /docs, /about, /merchant/login, /merchant/register, /merchant/dashboard, /merchant/projects, /merchant/orders, /merchant/addresses, /merchant/keys, /merchant/webhooks, /merchant/transactions, /merchant/products, /merchant/settings, /checkout/:token.

Original compatible external API: signed /v1/whoami, /v1/orders GET/POST, /v1/orders/:id GET, /v1/orders/:id/cancel POST. Canonical string METHOD\nPATH\nSORTED_QUERY\nSHA256_BODY\nTIMESTAMP\nNONCE, HMAC SHA256 hex, DJP-Key-ID/Timestamp/Nonce/Signature. Webhook envelope event_id,event_type,event_version:'v1',created_at,data; signature HMAC(secret,timestamp+'.'+raw_body), DJP-Webhook-ID/Timestamp/Signature. Nonce replay and project-scoped idempotency enforced.

`payments.allowFingerprintUnderpayment: true` in private server configuration opts into stablecoin fingerprint-only underpayment acceptance. It is off by default and does not change atomic token precision or locked quotes. Both exact and tolerant candidates are checked for ambiguity before automatic settlement. `order.paid` includes the actual `received_amount` and `waived_fingerprint_amount` where applicable; requested `payable_amount` remains the original quote. Paid GMV uses the real receipt at the original locked exchange rate.

Chain scanner module `server/chains.mjs` exports `registry`, `validateAddress(chain,address)`, `scanChain({chain,addresses,fromBlock,toBlock,config,fetchImpl?}) -> {transactions:[{id,chain,token_id,tx_hash,event_index,to_address,from_address,amount_atomic,block_height,block_hash,block_time,confirmations,confirmed,removed}],cursor,head}`. config from server-only JSON file/env; token contracts/mints/decimals explicitly configured and validated. Never trust symbols, external POSTs or browser state to settle live. Scanning includes persisted cursor, receipt success, canonical block, dedup tx+event, valid time window. Adapter errors leave cursor unchanged. Unsupported/unconfigured methods fail closed. The backend owns worker orchestration, scanner only network decoding.


## Conflict-only amount allocation

- Private configuration `payments.amountAllocation: 'conflict_only'`, `payments.conflictStep: '0.0000001'`, `payments.conflictTokens: ['bsc-usdt']` opts supported new amount-mode quotes into base-first allocation. An occupied amount increments by the exact token quantity, never by floating-point arithmetic. Unsupported token precision is rejected, not rounded.
- Public order `amount_matching` is null for other strategies; new quotes expose `{strategy:'conflict_only',base_amount,increment,adjustment,exact:true}` with decimal strings. They retain `payment_mode:'amount'` and `wallet_payment:null`; `payment_tolerance` must be null even when the legacy waiver is globally enabled.
- Allocation strategy and quote windows are retained with historical records. Legacy quote uniqueness and old order values remain intact. Conflict-only reuse requires non-overlapping quote windows and excludes unresolved payments; an already paid quote remains occupied through its original deadline.
- Match full network/token/address/atomic amount and a unique quote window, and retain immutable transaction bindings. A post-deadline late payment after amount reuse has no reliable order identity; do not claim that ordinary transfer matching can distinguish it from a new-order payment. See [pricing and limits](pricing.md#仅在冲突时增加金额).

## Wallet reference payments

- GET `/api/payment-policies` -> `{policies:[{project_id,payment_mode:'amount'|'reference',available_methods:[{chain,token_id}]}]}`. PUT `/api/projects/:id/payment-policy` `{payment_mode}` requires merchant ownership and the same Origin protection as other merchant writes. Only future orders inherit changed policy.
- Orders additionally expose `payment_mode`, `wallet_payment` and `fulfillment_status`. `wallet_payment` is null in demo; for configured live reference orders it contains `{chain_id,to,value:'0x0',data,recipient,token_symbol,token_decimals,amount,amount_atomic,reference,expires_at}`. Amounts remain exact strings. `reference` is a random nonzero 32-byte hex value. `fulfillment_status:'waiting_stock'` means confirmed funds await inventory; it is not a request for human payment approval.
- POST `/checkout/:token/demo-pay` simulates only demo orders on a demo app instance and returns public order state. The request body cannot choose amount, confirmation count or payment proof. It cannot settle live orders. A live wallet submission never calls this endpoint.
- `scanChain` optionally emits verified `payment_reference`; `payment_reference_invalid:true` forbids amount fallback when tagged input is malformed or mismatches the actual transfer. Core never accepts browser transaction hashes as settlement evidence. A current exact reference plus matching network/token/address/amount/time/confirmations is required for reference settlement, including manual claims.
- Reference quotes are base amounts without a fingerprint. Same-address/same-amount reservations are distinguished by `order_id` and permanent reference. Old amount orders retain their unique amount reservations and original behavior. Checkout methods use the order's frozen mode.
- `payments.automaticRecovery:true` enables persistent fair old-block retries and hourly continuing Webhook retries. `recoveryBatchSize` is a total per-tick block budget across chains, default 5, constrained to 1–50. Callbacks retain their event ID and body, and receivers must remain idempotent.

See [wallet flow and limits](wallet-payments.md) for encoding, buyer prerequisites and validation boundaries.
