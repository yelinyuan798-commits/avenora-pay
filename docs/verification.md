### BSC USDT 1.0 USDT 真实付款与自动发货

2026-11-04，用户通过钱包向配置的同一收款地址实际转入 1.0 USDT。独立只读核验确认网络为 BSC 主网（链 ID 56）、交易回执成功、USDT 转账日志的收款方及最小单位金额与订单一致，所在区块仍在主链；核验时已有438次确认，高于15次要求，区块时间位于订单有效窗口内。

平台中的商户、订单和交易均为 `live` 模式。订单自动变为 `paid`，`paid_source='chain'`，订单与交易双向绑定；未调用演示付款，也没有人工认单或补认记录。库存仅分配一份，买家页面显示已付款并交付商品，`order.paid` 仅产生一个独立事件。同一收款地址的另一金额订单仍为待付款，没有被这笔交易结算。间隔约90秒再次检查，库存交付和付款事件数量均未增加。

本次未配置外部商城 Webhook，通知状态为 `unconfigured`；付款事件已生成不代表外部商城已经收到通知。此节真实验收范围仅为本次 BSC USDT 1.0 USDT 原价订单，不能延伸为冲突尾数实付、其他链与币种或所有生产部署均已验收。后续 BNB 结果见下节。

## 2026-11-05 BNB 付款精度与历史款自动恢复

Node.js 26.4.0 下完整测试201项通过，生产前端构建通过。新增检查覆盖 BNB 六位付款精度、按币种配置的冲突步长、旧18位报价向上取到8位的受限兼容、同金额歧义和历史金额占用、少付和迟到拒绝、旧八位报价迁移、节点失败不结算、过期后重新扫描原区块、库存不足恢复、重组、重复事件、实收金额计费及通知。两实例部署前分别备份，数据库一致性副本连续初始化两次，原35张表的历史数据未被改写，完整性检查通过。

真实 BNB 测试首次未通过：有效付款窗内转入一笔小额 BNB，实际数量被缩短到8位小数，与旧18位报价不一致。BSC 主网成功回执及普通原生转账金额已核验，扫描器记录为金额不匹配，未发货。此失败记录保留，没有改写原报价掩盖精度差异；公开记录不包含付款人的地址、交易哈希、私有订单链接或精确付款时间。

2026-11-05 部署修复并显式启用旧 BNB 兼容后，常驻扫描任务重新读取原交易区块，达到确认要求后自动恢复原过期订单。订单与交易均为 `live`，`paid_source='chain'`，双向归属正确；核验时1630次确认，高于15次要求。系统保留旧应付金额与真实到账金额，自动恢复审计一条、人工认单零条、库存仅交付一份、独立 `order.paid` 事件一个；买家页面显示已付款与测试交付内容。实收计费按原锁价换算真实到账数量；未配置的外部商城 Webhook 仍不计为验收通过。

间隔约81秒复核，库存交付、付款事件和自动恢复审计数量仍各为一，扫描器持续追平，无恢复任务残留。部署版本另在一致性数据库副本中使用新鲜行情生成两单，数量分别为基础金额 `0.001394 BNB` 与冲突金额 `0.001395 BNB`，公共金额均不超过六位，未向真实库新增订单。

该结果证明此笔真实付款的自动补扫与补发。它不是原版本首次自动发货成功，也不替代新六位报价的首次主网付款验收。新报价使用最多六位小数，BNB 无冲突使用基础数量、有冲突增加 `0.000001 BNB`；USDT 既有规则不变。
