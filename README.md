
# Avenora Pay

**免费开源的 USDT（U）与多币种非托管收款平台，适用于数卡商城、独立站和自建业务系统。** 兼容 DujiaoPay 建单与签名通知协议，可对接 Dujiao-Next 等数卡商城，也可通过支付链接或 API / Webhook 接入其他收款场景。客户向商户自己的钱包转账，平台读取链上数据、核对订单并触发自动发货或签名通知。

[![一键部署到 Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/yelinyuan798-commits/avenora-pay)

[一键部署指南](docs/one-click-deploy.md) · [部署到自己的服务器](docs/deployment.md)

自建用户可点击按钮，在自己的 Render 账户部署网站和后台服务；**云计算与持久磁盘另行收费**，上线后需配置链节点和商户收款地址。使用运营者收款服务的商户，直接访问其网站注册即可，无需自行安装。

Avenora Pay 独立实现，采用 [MIT 许可证](LICENSE)，允许免费使用、商用、修改和分发，须保留许可证要求的版权与许可声明。内置的商户订阅收费模块是可选业务功能，不是使用本项目代码的授权费用。第三方材料保留各自许可，见 [第三方声明](THIRD_PARTY_NOTICES.md)。

*An open-source, self-hosted USDT and multi-asset payment platform with DujiaoPay-compatible APIs for Dujiao-Next integrations, payment links and automatic digital delivery. Non-custodial. MIT licensed.*

## 适用场景与商城接入

| 场景 | 接入与收款方式 |
| --- | --- |
| **Dujiao-Next 等数卡商城** | 通过 DujiaoPay 兼容接口创建订单、打开收银台；商城验证付款通知后，按自身流程自动发卡或交付数字商品。 |
| **独立站与其他电商系统** | 通过签名 API 创建支付订单、查询付款状态，使用 Webhook 将链上到账结果同步到商城。 |
| **分享链接收 U** | 创建固定金额或由付款人填写金额的支付链接，用于商品、服务或临时收款。 |
| **自带商品与自动发货** | 在商户后台配置数字商品和库存，付款确认后自动分配并交付库存内容。 |
| **面向多个商户提供收款服务** | 隔离各商户的项目、地址、订单和密钥，可选启用商户订阅套餐与账单。 |

普通地址转账模式下，客户扫码或复制收款地址付款，无需连接网站钱包；到账金额与确认要求以本单收银台为准。支持 USDT、USDC、BNB 等资产，具体可用币种和网络取决于部署配置。

**商城兼容说明：** 已按 Dujiao-Next 的 DujiaoPay 通道核对接口约定。传统独角数卡（dujiaoka）及其他商城版本需确认所用支付插件，必要时增加适配；外部商城的付款通知与自动发货仍需在实际部署中完成联调验收。接口与签名方式见 [接入约定](docs/contract.md) 和 [Node.js 接入工具](scripts/sdk.mjs)。

## 快速体验

需要 **Node.js 24 或以上**及 npm。

```sh
git clone https://github.com/yelinyuan798-commits/avenora-pay.git
cd avenora-pay
npm ci
npm run build
npm run dev
```

打开 <http://127.0.0.1:8787>，点击 **体验商户工作台**。服务会生成独立演示商户、测试地址、商品和订单；没有通用默认管理员账号或密码。创建商品订单后，可在收银台模拟到账并查看库存交付，也可体验订阅账单和套餐开通。

默认本地环境使用 `APP_MODE=demo`，演示报价固定，二维码不能用于付款。`npm run dev` 启动常驻服务并读取已经构建的前端；修改前端后需重新执行 `npm run build`。如果当前终端设置过 `NODE_ENV` 或 `APP_MODE`，请核对后再启动。

本地开发模式保留真实商户注册入口，真实商户仍须配置节点、报价和收款地址才能收款。**需要公开演示站时，应使用 `NODE_ENV=production` 与 `APP_MODE=demo`，并使用独立空数据库。** 配置方法见 [部署指南](docs/deployment.md)。

## 功能

- **多商户与多项目**：订单、收款地址、API 密钥、Webhook、商品和库存相互隔离。
- **收款与交付**：支持直接扫码或复制商户地址转账；可配置无冲突时按基础金额收款，冲突时按指定步长递增。另提供交易内订单标识的钱包支付方式。支持链上确认、事务内一次库存分配、签名通知及自动重试。
- **分享收款**：固定金额或买家自填金额的收款链接；退款模块登记商户申报的外部退款记录，未进行链上核验，也不替商户转币。
- **商户工作台**：收款统计、订单筛选、当前数据 CSV 导出、品牌展示、支持邮箱和手续费设置。
- **接入能力**：服务端 HMAC 签名、时间窗、请求防重放、建单幂等，以及 Node.js [接入工具](scripts/sdk.mjs)。
- **可选平台订阅**：套餐、月订阅账单、付款后开通、同档续费、宽限期、资源与 USD 计价额度，以及管理员审计记录。
- **账户安全**：密码哈希、会话失效、TOTP 两步验证和一次性恢复码；服务端密钥及商品库存加密存储。

平台不收集钱包私钥，不托管商户资产，也不执行提现或退款转账。它依赖所配置节点、行情来源和运行环境的正确性。

## 支持的资产与网络

主流资产包括 **BTC、ETH、BNB、SOL、TRX、USDT、USDC**，部分网络另支持 USDT0。注册表包含 11 条网络，但登记在注册表中不表示已经配置或验证可实收。

| 读取适配器 | 网络 |
| --- | --- |
| Bitcoin | Bitcoin 主网 |
| EVM | Ethereum、BNB Smart Chain、Polygon、Base、Arbitrum、Plasma、X Layer |
| TRON | TRON |
| Solana | Solana |
| Aptos | Aptos |

网络与币种必须同时匹配：例如 Ethereum、Base 和 Arbitrum 上的 ETH 是不同收款方式。同名稳定币也不能代替合约或 mint 身份核对。节点、网络标识、币种与扫描起点必须显式配置，未配置的真实方式不会开放。

金额以整数最小单位计算，付款数量以完整十进制字符串显示。服务端根据报价快照锁定应付金额；缺失或过期的行情会阻止新的真实报价。演示价格始终明确标为固定测试价格。详见 [链配置](docs/chains.md) 与 [报价和锁价](docs/pricing.md)。

BSC 原生 BNB 新报价最多保留6位小数，金额在服务端分配前取整，显示、复制和到账匹配保持一致；链上记录仍保留18位整数精度。旧18位报价的有限兼容与自动恢复需显式启用，范围见 [BNB 付款精度](docs/pricing.md#bnb-的付款精度与旧单兼容)。

**无需连接网站钱包的普通转账。** 项目使用金额识别，并启用 `conflict_only` 分配后，新订单首先尝试基础金额；同地址、同币种的金额被占用时才增加配置步长。BSC USDT 可配置为 `0.0000001`，同价订单依次为 `1.0`、`1.0000001`、`1.0000002`。收银台保留完整精度和复制入口，实际到账必须等于本单应付金额。配置及金额复用边界见[报价说明](docs/pricing.md#仅在冲突时增加金额)。

可选的“钱包支付自动认单”通过交易内订单标识区分同额订单。它需要客户从收银台连接钱包确认，不能用普通地址转账代替；兼容性与验收范围见[钱包支付说明](docs/wallet-payments.md)。

旧金额识别模式默认要求精确到账，也可显式开启稳定币“允许省略识别尾数”。多张订单均可能匹配时仍须核对；它不解决同价串单问题。配置与限制见[报价说明](docs/pricing.md#可选允许省略稳定币识别尾数)。

## 工作流程

1. 商户在后台或通过签名 API 创建订单。
2. 金额模式分配并锁定完整应付金额和付款窗口；可选钱包模式锁定基础金额与订单标识。
3. 金额模式的客户扫码或复制地址，按完整金额直接转账；可选钱包模式通过页面钱包按钮付款。
4. 扫描器校验实际链上交易及对应订单，并等待所需确认。
5. 支付确认后，在数据库事务内分配库存并记录通知事件；商城也可验证 Webhook 后自行履约。

浏览器跳转、钱包返回交易hash、客户端提交“已付款”或重复通知都不是付款证明。钱包支付模式可在重新验证规范链后，自动恢复原付款窗口内的迟扫款；超时付款和取消订单不会被猜测认领。旧金额模式的过期订单仍须显式复核。

## 部署

希望自动准备运行环境、HTTPS 入口和持久数据库，可使用顶部的 **Deploy to Render** 按钮，详见 [一键部署指南](docs/one-click-deploy.md)。已有服务器时按下方步骤部署。

应用需要常驻 Node.js 服务、后台扫描与通知任务、可写的 SQLite 数据库。它不能仅作为静态页面部署，目前按**单实例**设计。

仓库提供 `Dockerfile` 和 `compose.yaml`。当前 Compose 默认是 **live** 模式，并非一键演示配置：

```sh
cp .env.example .env
# 在本机编辑 .env，并准备私有 data/chains.json
# 完整步骤、演示覆盖配置与 HTTPS 反向代理要求见部署指南
docker compose config --quiet
docker compose up -d --build
```

生产启动必须提供有效的 64 位十六进制 `MASTER_KEY` 与 HTTPS `PUBLIC_BASE_URL`。仓库不附带真实节点凭据、商户地址或管理员身份。Docker 对主机只开放回环端口，HTTPS 由反向代理提供；反代信任需要按实际网络配置。

详见 [部署指南](docs/deployment.md)。如需向使用你部署平台的商户收费，再阅读 [平台订阅说明](docs/billing.md)。

## 当前边界

- ETH / BNB 只识别钱包直接转账的顶层交易值；TRX 只识别标准成功 `TransferContract`，不识别合约内部 TRX 转账。
- BTC 不以 mempool 广播时间确认付款；需要在付款窗口内进入区块，随后等待确认。默认 6 次确认，不能保证绝对不会重组。
- Solana 内部指令需要完整且可核对的成功调用日志；不支持 Token-2022。Aptos 支持当前实现的 Fungible Asset primary store 路径。
- 旧金额模式永久保留金额占用；`conflict_only` 新报价按付款窗口分配，不能把原窗口尚未结束的已付款金额立即释放。过期后才转入的旧单款与新窗口的同额付款仍可能无法区分，客户必须遵守付款截止时间，不能忽略本单尾数。钱包模式可用永久订单标识区分同额款。
- 订阅不自动扣款，不做跨档余额折算；没有接入邮件验证、邮件找回、Telegram 或邀请码系统。
- 未完成全网络真实入账、长期负载、完整故障恢复和独立安全审计。
